# werewolf-engine 固化复盘与避坑指南

> 记录 2026-08-16 将 werewolf-engine 从动态插件固化（`dsh plugin add` → web profile）后引发的两起事故的**完整根因、修复与验证**，以及下次固化插件时必须逐条对照的避坑清单。

---

## 一、结论速览（TL;DR）

| 现象 | 根因 | 修复 |
|---|---|---|
| 固化后 dsh 一跑就崩：`Cannot read properties of undefined (reading 'prepare')` | `@deepseek-ai/dsh-tools` 出现**多份物理副本** → ESM 模块身份（realpath）不同 → `TOOL_RUNTIME_SCHEDULER` **Symbol 身份不匹配**（ESM dual-package hazard）→ `ctx.tools[Symbol]` 为 undefined | 消灭多余副本，让所有解析路径 realpath 收敛到全局 dsh 唯一副本；插件依赖改用 `link:` 协议托管 |
| 启动日志：`[werewolf] subagents/agents/tools services unavailable`，且 werewolf_* 工具从未注册 | 固化插件**没有声明 `inject`** → Cordis loader 并行启动时立即执行 apply，早于三个服务的提供方 fiber 激活 → `ctx.get()`（strict）返回 undefined → 早退、永不重试 | 插件声明 `inject: ['subagents', 'agents', 'tools']`，让 Cordis 服务驱动激活 |

## 二、问题一：`Cannot read properties of undefined (reading 'prepare')`

### 2.1 现象

固化（`dsh plugin --profile web add ./werewolf-engine`）并重启 dsh web 后，运行任何一轮 agent 循环直接报：

```
本轮运行失败 Cannot read properties of undefined (reading 'prepare')
```

### 2.2 根因链

1. **报错点**在 `dsh-agent-loop`（全局 dsh 包）的工具调度：
   ```js
   // @deepseek-ai/dsh-agent-loop/lib/index.js:193
   const prepared = await ctx.tools[TOOL_RUNTIME_SCHEDULER].prepare(call.exec)
   ```
   `TOOL_RUNTIME_SCHEDULER` 是 `Symbol("@deepseek-ai/dsh-tools.scheduler")`，以 **Symbol 为键**挂在 `tools` 服务实例上。

2. **ES 模块身份 = 文件真实路径（realpath），不是包名/内容**。同一个包名若存在于两个不同物理路径，Node 会加载出两个互不相干的模块实例，各自导出的 Symbol 是不同对象。

3. **固化动作引入了三份 dsh-tools 物理副本**：
   - `dsh plugin add` 把 `@deepseek-ai/dsh-tools` 自动写进了 `profiles/web/package.json` 的 `dependencies`；
   - pnpm 因此把 dsh-tools 作为**独立副本**装到 `profiles/web/node_modules/@deepseek-ai/dsh-tools`，**shadow 掉了** `profiles/node_modules/@deepseek-ai/dsh-tools`（原本是指向全局 dsh 的 junction）；
   - werewolf-engine 自己的 `package.json` 也声明了 `"@deepseek-ai/dsh-tools": "^0.1.0-rc.6"`，其 `node_modules` 里又装了**第三份**（pnpm store 副本）。

4. 于是同一进程内出现多个 dsh-tools 模块实例：

   | 消费方 | 解析到的路径 |
   |---|---|
   | cordis loader（`baseUrl=profiles/web`） | `profiles/web/node_modules/@deepseek-ai/dsh-tools`（本地副本） |
   | `dsh-agent-loop`（全局 dsh 静态 import） | 全局 dsh 的副本 |
   | werewolf-engine（link 包，从真实路径 `D:\agentWorkSpace` 解析依赖） | `werewolf-engine/node_modules` 里的副本 |

   → dsh-agent-loop 用自己副本的 Symbol 去 `ctx.tools`（另一副本构造的服务）上取值 → `undefined` → `undefined.prepare()` 崩溃。

### 2.3 修复（已执行）

1. 从 `profiles/web/package.json` 移除 `@deepseek-ai/dsh-tools` 直接依赖，`pnpm install` 清掉 `profiles/web/node_modules/@deepseek-ai/` 下的本地副本（现为空，`@deepseek-ai/dsh-tools` 解析回落到 `profiles/node_modules` 的 junction → 全局副本）。
2. 消灭 werewolf-engine 本地副本：删除其 `node_modules/@deepseek-ai/dsh-tools`（pnpm store 副本），原地建 **junction 指向全局 dsh 的 dsh-tools**（插件从真实路径 `D:\agentWorkSpace` 解析依赖，所以 junction 必须建在插件自己的 node_modules 里）。
3. **加固（2026-08-16 本次新增）**：`werewolf-engine/package.json` 把 dsh-tools 从 registry 版本改成 `link:` 协议直接指向全局副本，pnpm 把它当 link 依赖托管，**后续任何 `pnpm install` 都是幂等的**，不会再重新引入 store 副本：
   ```json
   "dependencies": {
     "@deepseek-ai/dsh-tools": "link:<全局dsh安装路径>/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/dsh-tools"
   }
   ```

### 2.4 验证（已跑通）

```powershell
# ① 三处解析路径的 Target 必须收敛到同一个全局路径
Get-Item %USERPROFILE%\.dsh\profiles\node_modules\@deepseek-ai\dsh-tools -Force | Select Target
Get-Item D:\agentWorkSpace\werewolf-engine\node_modules\@deepseek-ai\dsh-tools -Force | Select Target
# 两者都应输出 → <全局dsh安装路径>/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/dsh-tools

# ② 模块实例 / Symbol 必须全等（把 <全局dsh安装路径>/<工作区>/<profile> 替换为实际路径）
node --input-type=module -e "const a=await import('file:///<全局dsh安装路径>/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/dsh-tools/lib/index.js'); const b=await import('file:///<工作区>/werewolf-engine/node_modules/@deepseek-ai/dsh-tools/lib/index.js'); const c=await import('file:///%USERPROFILE%/.dsh/profiles/node_modules/@deepseek-ai/dsh-tools/lib/index.js'); console.log('same instance:', a===b && a===c); console.log('same symbol:', a.TOOL_RUNTIME_SCHEDULER===b.TOOL_RUNTIME_SCHEDULER && a.TOOL_RUNTIME_SCHEDULER===c.TOOL_RUNTIME_SCHEDULER)"
```
期望输出：`same instance: true` / `same symbol: true`。

## 三、问题二：`[werewolf] subagents/agents/tools services unavailable`

### 3.1 现象

修复 prepare 崩溃后重启，dsh 能正常起来，但启动日志出现：

```
[werewolf] subagents/agents/tools services unavailable
```

且 `werewolf_*` 工具**从未注册**——插件等于没加载成功（只有加载、没有功能）。

### 3.2 根因链

1. **loader 对所有插件行是并行启动的**（`cordis-plugin-loader/lib/index.js`：`Promise.allSettled(config.map(o => this.create(o)))`），不存在"按行顺序先就绪再加载"的保证。
2. **不声明 `inject` 的插件会立即 apply**：Cordis 里 fiber 的启动条件由注入依赖决定（`_refresh/_setEpoch`），inject 为空 → epoch 立即非 INACTIVE → `_reload()` 立刻执行 `apply(ctx)`，不等待任何服务。
3. `subagents / agents / tools` 分别由 `dsh-subagent / dsh-agent / dsh-tools` 提供，都是大模块，import + apply 较慢；而 `ctx.get(name)` 默认 `strict=true`，**要求提供方 fiber 已 active（state===2）**，否则返回 `undefined`（cordis `get/_getImpl`）。
4. 固化版 `lib/index.js` 的兜底逻辑是"一次失败永久退出"：
   ```js
   if (!subagents || !agents || !tools) {
     console.error('[werewolf] subagents/agents/tools services unavailable')
     return            // 早退，且没有监听 service/available 重试 → 工具永不注册
   }
   ```

### 3.3 修复（已执行）

在插件对象上声明 `inject`，让 Cordis **服务驱动激活**——三个服务全部可用（提供方 fiber active）后才执行 apply：

```js
export default {
  inject: ['subagents', 'agents', 'tools'],
  apply(ctx) { /* 原逻辑不变，ctx.get 现在必然命中 */ }
}
```

> 通用规律：**任何固化（静态）插件必须把消费的服务声明为 `inject`**，不要赌"启动时服务恰好就绪"。动态插件场景下沙箱 ctx 的 `tools/subagents/agents` 早已就绪，所以动态版没暴露这个问题——这正是动态版能跑、固化版不能跑的差异点。

## 四、避坑清单（下次固化插件前逐条过）

1. **`@deepseek-ai/*` 包全进程只允许一份物理副本（全局 dsh 那份）**
   - `dsh plugin add` 会把 `@deepseek-ai/dsh-tools` 写进 profile 的 `dependencies`——这就是上次的祸根。装完立即检查：
     ```powershell
     Get-Content $env:USERPROFILE\.dsh\profiles\web\package.json   # dependencies 里绝不能出现 @deepseek-ai/* 的 registry 版本
     Get-ChildItem $env:USERPROFILE\.dsh\profiles\web\node_modules\@deepseek-ai   # 应为空
     ```
   - 或者干脆**不用 `dsh plugin add`**，手动三步：改 `package.json`（`dependencies` 加 `link:` 条目 + `dsh.profile.bundles` 加包名）→ `pnpm install` → 复查 lockfile 没有引入 @deepseek-ai 本地副本。
2. **插件包自身依赖 `@deepseek-ai/dsh-tools` 必须用 `link:` 指向全局副本**（见 2.3），禁止写 registry 版本号；改完必须 `pnpm install` 并复查 `node_modules/@deepseek-ai/dsh-tools` 是 junction/symlink 且 Target 是全局 dsh 路径。
3. **固化插件必须声明 `inject`**（服务驱动激活），禁止裸 `ctx.get()` 后早退。
4. **link 包的依赖解析基于真实路径**：插件从 `D:\agentWorkSpace\werewolf-engine` 解析依赖，**不会**用 profile 的 node_modules——所以插件**自己的 node_modules** 才是重点排查对象（junction 就建在这里）。
5. **Client 半（人类席位 UI）不能直接固化**：`harness.handle` / `host.call` 是动态沙箱 builtin，正式插件需要 `ctx.remote`（Typert Remote）打包 client 产物，尚未实现 → 人类席位继续以动态插件（`cordis_define` 完整 host+client 源码）方式运行。
6. **改完必须重启 dsh web 验证**：启动日志应无 `[werewolf] ... unavailable`、无 prepare 崩溃，并出现 `[werewolf] plugin v32 active`；再跑 `werewolf_start` 冒烟。
7. 已固化的运行时残留：`werewolf-engine/node_modules/.pnpm` 里可能残留旧 store 目录（未被 `.package-map.json` 引用、无害），`pnpm install` / `pnpm prune` 可清。
